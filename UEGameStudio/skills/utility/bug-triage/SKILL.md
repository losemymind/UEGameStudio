# 缺陷分诊

把开放 bug 积压处理成有优先级、已分配冲刺的行动清单。区分**严重度**（影响有多坏）与**优先级**（要多紧急修），检测系统性趋势，确保没有关键 bug 在冲刺之间丢失。

## 何时使用
- 冲刺开始，把开放 bug 分配到新冲刺或积压
- `/team-qa` 完成并归档新 bug 后
- 开放 bug 数超过 10 个需要重排时

## 流程
### 解析参数
1. 模式：`sprint`（针对当前冲刺）/ `full`（全量）/ `trend`（仅趋势，只读）/ 无参数（有当前冲刺则 sprint，否则 full）。

### 加载 bug 积压
1. 按优先级 Glob：`production/qa/bugs/*.md` → `production/qa/bugs.md` → QA 计划 Bugs Found 表；无 bug 则停止。
2. 读最近冲刺文件了解当前冲刺与容量；读 `coding-standards.md` 的严重度定义（缺则用标准定义）。

### 分类每个 bug
1. 严重度：S1 崩溃/丢数据/功能完全失效 / S2 主要功能坏但可玩 / S3 功能降级有变通 / S4 视觉瑕疵/拼写。
2. 优先级：P1 本冲刺修 / P2 尽快修 / P3 积压 / P4 不修或延期。
3. 分配：P1/P2 在 sprint 模式下按容量分配到冲刺或标记 overflow。
4. 偏差检查：同系统 3+ bug、同 story 2+ S1/S2、对已标记 Complete 的 story 提 bug（= 回归）。

### 趋势分析
1. 量趋势（开放/本冲刺新开/关闭/净变化）、系统热点（最多 bug、最高 S1/S2 比）、年龄（超过 2 冲刺、未分配 S1/S2）、回归指标。

### 生成分诊报告
1. 输出 Triage Summary、P1/P2/P3-P4 表、系统性议题、趋势分析、推荐行动。

### 写入与设门
1. 经确认写入 `production/qa/bug-triage-[date].md`；按未分配 S1、回归、无 P1 情况给出后续指引。

## 输入/输出
- 输入：开放 bug 文件、冲刺计划、严重度定义
- 输出：分诊报告（`production/qa/bug-triage-[date].md`）

## 约束
- 未经批准，永不关闭 bug 或标记 Won't Fix——作为 P4 候选列出并询问。
- 永不自动分配到已满的冲刺——标记 overflow 让冲刺负责人决定取舍。
- 严重度客观、优先级是团队决策——分类是建议而非命令。
- 趋势数据仅供参考，不单独据此阻塞工作。

## 反例（不要这样）
- 混淆严重度与优先级——"影响坏"不等于"要现在修"。
- 自动把 bug 塞进已满冲刺——容量溢出应显式标记并交冲刺负责人决策。
- 擅自关闭或标记 Won't Fix——需要用户批准。
- 只分诊不分析系统热点与回归趋势——错过重复出现的设计/质量问题。

## 反合理化表（借口 → 反驳）
| 借口（会怎么说） | 反驳（为什么不对） |
|---|---|
| 「S1 影响这么坏，当然要 P1 现在修」 | 严重度是"多坏"、优先级是"多急"，混淆二者会扭曲团队决策。 |
| 「这几个 bug 明显没人管，标 Won't Fix 吧」 | 关闭/标记 Won't Fix 需用户批准，擅自处理会掩盖真实决策责任。 |
| 「冲刺满了就塞进去吧」 | 满容量必须标记 overflow 交冲刺负责人取舍，强行塞入制造不可控风险。 |

## Red Flags（违规信号）
- 报告中每个 bug 只出现一个等级字段（严重度与优先级被合并）。
- 直接把 bug 写入已满冲刺而非标记 overflow。
- 未询问就关闭或标记 Won't Fix。

## Verification（证据化验证门）
- [ ] 报告区分严重度与优先级两类字段，且 P1/P2/P3-P4 表完整。
- [ ] 检测到系统热点与回归趋势（同系统 3+ bug、对 Complete story 提 bug 等）并写入报告。
- [ ] 无未经批准的关闭/Won't Fix；满冲刺分配均标 overflow。
