# 技能测试

## 何时使用
- 新增或修改技能后，检查其结构是否合规
- 需要验证技能的实际行为是否满足测试规范中的断言
- 需要全局盘点哪些技能/agent 缺少测试规范（覆盖率缺口）
- 需要确认技能的前置元数据（frontmatter）是否完整

## 流程
### 解析参数
1. 根据第一个参数判定模式：`static` / `spec` / `audit`。
2. 参数缺失或无法识别时，输出用法说明并停止。

### static 模式：结构静态检查
1. 逐项执行 7 项检查：frontmatter 必填字段、是否含多阶段标题、是否有判定关键词（PASS/FAIL/CONCERNS/APPROVED/BLOCKED 等）、是否含"先问再写"协作语言、是否有下一步交接、`context: fork` 时是否 ≥5 阶段、argument-hint 是否合理。
2. 输出单技能逐项 PASS/WARN/FAIL 报告；`static all` 时输出汇总表与不合规清单。

### spec 模式：行为评测
1. 从 catalog 定位技能的测试规范路径，读取技能文件与规范文件。
2. 对每个测试用例的每条断言，判断"遵循该技能指令是否满足断言"，标记 PASS / PARTIAL / FAIL。
3. 逐项核对协议合规断言（是否先问再写、是否先呈现发现再求批准、是否有下一步交接）。
4. 输出逐用例报告与总体判定；询问是否写回结果并更新 catalog 的测试日期。

### audit 模式：覆盖率报告
1. 读取 catalog，枚举全部技能与 agent。
2. 逐项核对是否已有 spec、最近各模式测试日期与结果、优先级。
3. 输出技能/agent 覆盖率表与"优先级缺口 Top5"。此模式不写文件。

## 输入/输出
- 输入：技能名（或 `all`）、目标技能文件、catalog 与测试规范文件。
- 输出：结构化检查报告（逐项 PASS/WARN/FAIL）、覆盖率表、总体判定（COMPLIANT/WARNINGS/NON-COMPLIANT）。

## 约束
- 必须逐项执行全部 7 项检查，不可跳过。
- spec 模式是推理评测，不做代码执行。
- audit 模式只读，不写任何文件。
- 任何写操作（结果文件、catalog 更新）必须先征得用户同意（"May I write..."）。

## 反例（不要这样）
- 只看 frontmatter 就下结论，跳过行为/交接/协作语言检查。
- 在 audit 模式下擅自写入结果文件。
- 把 spec 断言当作代码可执行测试，用真实编译去验证。
- 把"正文有相关小节"当作断言通过，而不核对 expect 的每一条（含否定性断言）。
