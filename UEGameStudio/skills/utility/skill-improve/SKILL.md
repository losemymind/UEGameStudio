# 技能改进

## 何时使用
- 技能未通过 static 或 category 检查（存在 FAIL/WARN）
- 需要以可验证的方式提升技能质量，而非盲改
- 需要"改进可回滚"的保障（分数不升则回退）

## 流程
### 解析参数
1. 读取技能名，验证 `SKILL.md` 存在；缺失则输出用法并停止。

### 基线测试
1. 跑 static 检查记录基线（FAIL 数、WARN 数、具体失败项）。
2. 若 catalog 有 category 字段，再跑 category 检查记录基线。
3. 若两者均零失败零警告，停止并报告"无需改进"。

### 诊断
1. 通读技能文件，为每个失败/警告定位精确缺口（缺失字段、阶段数不足、无判定词、有写权限却无"先问再写"语言等）。
2. 汇总展示完整诊断，先给用户看，再提修改。

### 提出修复
1. 为每个失败项写针对性最小修复，用 before/after 块展示，只改失败处。
2. 询问是否写入改进版；用户拒绝则停止。

### 写入与复测
1. 记录原文件内容（用于回滚），写入改进版，复测 static（及 category）。
2. 展示前后分数对比与综合变化（improved / no change / worse）。

### 判定
1. 计算综合失败总数（static+category 的 FAIL+WARN）。
2. 分数改善则保留；持平或变差则询问是否用 git 回滚。

## 输入/输出
- 输入：技能名、该技能的 SKILL.md、catalog 中的 category 字段。
- 输出：改进后的 SKILL.md、前后分数对比、保留/回滚判定。

## 约束
- 只改失败的检查项，不重写已通过的段落。
- 写文件前必须先展示诊断与 before/after 并征得同意。
- 分数不升必须回滚，保证基线单调不降。
- 回滚用 `git checkout`，需用户确认。

## 反例（不要这样）
- 跳过基线直接改，导致无法判断是否真的改善。
- 借"改进"顺带重写大量已通过的章节。
- 分数变差仍保留改动，或不提供回滚。
- 未把诊断展示给用户就擅自写文件。

## 反合理化表（借口 → 反驳）
| 借口（会怎么说） | 反驳（为什么不对） |
|---|---|
| 「先改起来再说，基线回头补」 | 约束「跳过基线直接改」会导致无法判断是否真改善，反例已禁止。 |
| 「顺手把其他过时段落一起重写，整体更干净」 | 约束「只改失败项，不重写已通过段落」。 |
| 「分数变差一点但改动更优雅，保留吧」 | 约束「分数不升必须回滚，保证基线单调不降」。 |
| 「改动很小，直接写文件不用先给用户看」 | 约束「写前必须展示诊断与 before/after 并征得同意」。 |

## Red Flags（违规信号）
- 无基线记录（FAIL/WARN 数与具体失败项）就进入修改。
- 改动范围超出失败项，重写已通过章节。
- 复测分数持平或变差却保留改动，或未提供回滚。
- 写文件前未展示诊断与 before/after diff。

## Verification（证据化验证门）
- [ ] transcript 有 static（及 category）基线结果，含 FAIL/WARN 数与失败项清单。
- [ ] 每次写前有 before/after 块展示与用户同意记录。
- [ ] 复测后有前后分数对比与综合变化（improved/no change/worse）判定。
- [ ] 分数不升时提供并执行了 git 回滚（需用户确认）。
