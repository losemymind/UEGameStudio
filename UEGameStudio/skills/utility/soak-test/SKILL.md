# 长时间浸泡测试

浸泡测试（耐力测试）是带特定观察目标的长时游玩会话。与冒烟（关键路径、约 10 分钟）或单功能试玩（约 30 分钟）不同，浸泡测试跑 30 分钟到数小时，用于暴露：内存泄漏、性能漂移、状态累积 bug、乐趣疲劳、内容耗尽。**本技能生成观察协议与分析框架——真正游玩的是人。**

## 何时使用
- Polish 阶段、`/gate-check release` 之前
- 修复某个内存/稳定性问题后（回归浸泡）
- 长期游玩从未被正式跟踪时

## 流程
### 解析参数
1. 时长（默认 `1h`）：30m/1h/2h/4h；焦点（默认 `all`）：memory/stability/balance/all。

### 加载上下文
1. 读取技术偏好（引擎、性能预算：内存上限/目标 FPS/帧预算）、game-concept（预期会话时长、核心循环）、最近的试玩记录、最近的 QA 计划。

### 定义观察检查点
1. 按时长生成定时检查点（如 1h：T+0/T+15/T+30/T+45/T+60）。

### 生成观察协议
1. 内存/稳定性观察项，按引擎监控：
   - Godot：Debugger → Monitors，跟踪 Static Memory 与 Object Count。
   - Unity：Memory Profiler，记录 Total Reserved Memory / GC Allocated / Object Count。
   - Unreal：每个检查点用 `stat memory`，记录 Physical Memory Used / Available，全程增长 >50MB 告警。
2. 稳定性观察项：无崩溃/挂起、帧率达标、音频正常、HUD 正常、输入正常。
3. 平衡/疲劳观察项：核心机制是否仍有奖励感、难度感知、新颖内容耗尽、挫败/巅峰时刻。

### 生成协议文档
1. 生成含 Pre-Session 设置、T+0 基线、检查点日志、会话后分析（内存趋势/稳定性摘要/疲劳摘要/问题清单）、PASS / PASS WITH CONCERNS / FAIL 结论与签字的完整协议文档。

### 写输出
1. 经确认写入 `production/qa/soak-test-[date]-[duration].md`，并给出运行指引。

## 输入/输出
- 输入：引擎与性能预算、会话设计意图、历史试玩/QA 记录
- 输出：浸泡测试协议文档（`production/qa/soak-test-[date]-[duration].md`）

## 约束
- 本技能生成协议、由人执行——绝不自动跑浸泡测试（观察需要真人）。
- 时长应匹配游戏的会话设计；首次浸泡用 `all` 焦点（窄焦点用于特定修复后的回归浸泡）。
- 写文件前必须确认。

## 反例（不要这样）
- 试图自动运行浸泡测试——观察类指标（疲劳、挫败、内容耗尽）必须由人判定。
- 对 5 分钟的游戏硬套 4 小时浸泡——时长应匹配会话设计。
- 首次就只做 memory 窄焦点——窄焦点是回归浸泡用的，不是首轮。
- 未经确认就创建协议文件。

## 反合理化表（借口 → 反驳）
| 借口（会怎么说） | 反驳（为什么不对） |
|---|---|
| 「我写个脚本自动跑浸泡，效率高」 | 约束「绝不自动跑浸泡测试」，疲劳/挫败/内容耗尽必须由人判定。 |
| 「5 分钟的小游戏我也给 4 小时协议」 | 反例「对 5 分钟游戏硬套 4 小时」，时长应匹配会话设计。 |
| 「首轮就只盯 memory 焦点最聚焦」 | 约束「首次浸泡用 all 焦点」，窄焦点用于特定修复后的回归浸泡。 |
| 「协议文件直接创建」 | 约束「写文件前必须确认」。 |

## Red Flags（违规信号）
- 尝试自动执行/运行浸泡测试会话。
- 时长与会话设计明显不匹配（未读 game-concept 预期会话时长）。
- 首次浸泡就用窄焦点（memory/stability/balance 之一）而非 all。
- 未经确认创建协议文件。

## Verification（证据化验证门）
- [ ] 协议文档含 Pre-Session 设置、T+0 基线、定时检查点日志、会话后分析（内存趋势/稳定性/疲劳摘要/问题清单）与结论。
- [ ] 检查点按时长生成（如 1h → T+0/15/30/45/60），时长与 game-concept 会话时长一致。
- [ ] 引擎对应监控项正确（Unreal 用 stat memory 记录 Physical Memory Used/Available，>50MB 告警）。
- [ ] 输出为协议文档（由人执行），无自动运行行为；写前有确认记录。
