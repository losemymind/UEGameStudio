# 工作量估算

## 何时使用
- 任务进入 sprint 前的工期估算
- 需求模糊需要时间盒/尖峰验证时
- 超过 10 天的任务需要拆分时

## 流程
### 1. 理解任务
- 读取任务描述；过于模糊则先澄清
- 读取项目上下文（技术栈、规范、架构模式、估算准则）
- 读相关 GDD

### 2. 扫描受影响代码
- 识别需改动的文件/模块，评估复杂度、集成点、现有测试覆盖
- 读取历史 sprint 数据与速率

### 3. 分析复杂度因素
- 代码复杂度：受影响文件行数、依赖与耦合、核心 vs 叶子代码、是否有现成模式可循
- 范围：涉及系统数、新写 vs 修改、新增测试覆盖量、数据迁移/配置
- 风险：新技术/陌生库、需求模糊、依赖未完成工作、跨系统集成、性能敏感

### 4. 生成估算
- 复杂度评估表、关键受影响文件
- 工作量区间表：乐观/期望/悲观三天场景，推荐预算取"期望"
- 置信度（High/Medium/Low）+ 风险因素表 + 依赖表 + 建议拆分表

## 输入/输出
- 输入：任务描述 + 相关代码/GDD + 历史速率
- 输出：结构化估算报告（含区间、置信度、最大风险）

## 约束
- 只读报告，不写文件
- 始终给区间（乐观/期望/悲观），不给单一数字
- 推荐预算用期望值而非乐观值
- 按半天粒度取整；不静默加缓冲，显式列出风险

## 反例（不要这样）
- 只给一个精确数字（暗示虚假精度）
- 用乐观值当推荐预算
- 静默加缓冲而不说明风险
- 模糊任务不做澄清直接估算

## 反合理化表（借口 → 反驳）
| 借口（会怎么说） | 反驳（为什么不对） |
|---|---|
| 「给个精确数字看起来更专业」 | 单一数字是虚假精度，必须给乐观/期望/悲观区间 |
| 「用乐观值当预算，团队会更拼」 | 推荐预算必须用期望值，用乐观值是误导排期 |
| 「我加个缓冲，就不用解释风险了」 | 禁止静默加缓冲，风险必须显式列入风险表 |

## Red Flags（违规信号）
- 输出只有一个数字，无乐观/期望/悲观区间
- 推荐预算取乐观值而非期望值
- 模糊任务未澄清直接给出估算

## Verification（证据化验证门）
- [ ] 含乐观/期望/悲观三档区间，推荐预算取期望值
- [ ] 含置信度（High/Medium/Low）与风险因素表、依赖表
- [ ] 按半天粒度取整，无静默缓冲，风险显式列出
- [ ] 模糊任务已先澄清（有澄清记录）
