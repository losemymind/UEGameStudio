# 需求发现

## 何时使用
- 概念阶段尚未明确目标玩家、核心问题、平台、商业/合规或成功指标。
- 现有需求无法写成验收标准，或多个 stakeholder 目标冲突。

## 流程
1. 读取 workflow catalog 的 concept entry/exit、已有 concept/GDD/调研；先列已知、假设、未知，禁止重复问已有答案。
2. 分轮请求用户输入：目标玩家与核心幻想；核心循环和失败体验；平台/输入/联网；内容/商业化/地区；性能、无障碍、隐私、安全、进度与预算。
3. 对每项记录 ID、来源、理由、优先级、验收方法、owner、依赖、状态；事实与假设分栏，冲突不擅自裁决。
4. 用 Given/When/Then 或可量化阈值写验收标准；版本敏感 UE 结论交给 `ue-source-verification`。
5. 建需求追踪矩阵（需求→GDD/ADR/story/test/evidence）；给出 MVP、非目标、风险和待决策清单。
6. 展示草稿并请求批准后，最小写入 `design/requirements/baseline.md` 与 `design/registry/requirements.yaml`。
7. 只有最小可验证结果、非目标和风险接受记录均明确时才可标 `Ready`；模糊目标必须拒绝标 Ready，并列出待决问题与风险 owner。

## 输入/输出
- 输入：用户想法、业务/玩家目标、平台与约束、已有文档。
- 输出：需求基线、注册表、开放问题与追踪矩阵。

## 约束
- 不把 agent 推断写成用户事实；不默认平台、联网、商业化或合规范围。
- 写盘前请求批准；更新只改本轮已批准条目。

## 反例
- 一次问几十个开放问题，或明知答案仍追问。
- 把“好玩”“性能好”当可验收需求。
- 未批准就覆盖需求注册表。

## 反合理化表
| 借口 | 反驳 |
|---|---|
| “先做起来再说” | 未定义目标与验收会把探索成本转成返工。 |
| “UE 默认值够用” | 平台和版本会改变默认值，须验证并显式记录。 |

## Red Flags
- 需求无来源、owner 或验收方法。
- 假设被写成已确认事实。
- 修改超出批准范围。

## Verification
- [ ] 每个需求有 ID/来源/优先级/验收/owner/依赖/状态。
- [ ] 事实、假设、未知、冲突与非目标清晰分离。
- [ ] 需求可追踪到设计、实现、测试和证据。
- [ ] 未批准时文件系统不变。
