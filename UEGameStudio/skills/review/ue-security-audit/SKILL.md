# UE 安全审计

## 流程
1. 确定范围、构建/commit、资产与数据流；列信任边界：client、dedicated/listen server、backend、platform SDK、UGC/CDN、CI/signing。
2. 建威胁模型：身份/授权、RPC/复制、反作弊、输入与反序列化、存档/配置、网络传输、secret、插件/依赖、pak/IoStore、日志/隐私、管理面。
3. 源码审查：服务端是否重新校验客户端输入/速率/ownership；RPC validation、权限提升、路径/命令注入、敏感日志、硬编码凭据、不安全随机、未固定依赖。
4. 运行项目已有静态/依赖/secret 检查；工具结果需手工确认，禁止把未验证扫描器输出当漏洞事实。动态或攻击性测试须单独授权并限定非生产目标。
5. 每项记录 severity、CWE/类别、证据路径/行、利用前提、影响、修复、owner、验证与误报状态；由 security-engineer 和 UE 专项 reviewer 复核。
6. 输出 PASS/CONDITIONAL/FAIL；Critical/High 未关闭或无到期例外不得进 release readiness。
7. **只读审计模式**：不修改 `Source/`、`Config/`、插件或 CI，不触发动态攻击/外部扫描；先展示报告，获批后才保存报告文件，未批准时文件系统保持不变。

## 约束
- 只审计授权范围；不利用真实玩家/生产系统，不外传源码或 secret。
- 默认只读；报告保存也属于写入，必须先获得明确批准。
- 客户端永不被视为权威；加密不是授权或服务端验证的替代。

## 反例
- 看到 Server RPC 就默认安全。
- 扫描器报 High 就不核实地宣布可利用。
- 为验证漏洞攻击生产服务。

## 反合理化表
| 借口 | 反驳 |
|---|---|
| “客户端有反作弊所以可信” | 客户端由攻击者控制，业务授权仍须服务端执行。 |
| “扫描器标 High 就必须是真漏洞” | 严重度需要可达性、前提和影响的人工证据。 |

## Red Flags
- 未画信任边界就审 RPC/支付/UGC。
- 扫描器输出没有代码上下文或误报状态。
- 动态测试缺书面范围和非生产目标。

## Verification
- [ ] 信任边界和资产/数据流完整。
- [ ] 发现项有代码证据、利用前提、严重度、owner 和复测方法。
- [ ] 动态测试有明确授权和非生产范围。
- [ ] 只读审计未修改源码/配置或外部状态。
