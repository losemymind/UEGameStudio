# 内部变更日志

## 何时使用
- 生成某版本/sprint 的**内部**变更日志（技术向）
- 需要记录新功能/改进/Bug 修复/平衡/技术债的完整明细
- 需要为 `/patch-notes`（玩家向）提供上游输入

> **分工**：本技能只产出**内部版**（开发者/QA 用，含提交/负责人/文件路径）。**玩家向版本**（把开发者语言翻译为玩家语言）是 `patch-notes` 的职责——两者不要混做。生成玩家向说明请运行 `/patch-notes`；需要玩家向产出时，本技能提示走 patch-notes 而非自行生成。

## 流程
### 阶段 1：解析参数
- 读版本或 sprint 编号（版本对应 git tag，sprint 对应日期范围）；`git rev-parse` 确认是 git 仓库，否则优雅中止

### 阶段 2：收集变更数据
- `git log [last-tag]..HEAD`（无 tag 读近 100 条）；读 sprint 报告与已完成设计文档理解上下文

### 阶段 3：分类变更
- 归入：新功能/改进/Bug 修复/平衡调整/已知问题/杂项
- 检查提交信息是否含任务引用（`[STORY-123]`、`#NNN` 等），统计无引用提交数

### 阶段 4：生成内部变更日志
- 按模板输出：新功能（含提交/负责人/设计文档链接）、改进、Bug 修复、平衡、技术债/重构、杂项、已知问题、指标

### 阶段 5：玩家向移交（不自行生成）
- 若用户需要玩家向补丁说明，**提示运行 `/patch-notes`** 并移交内部版为输入；不自行翻译生成
- 仅当明确无 patch-notes 需求时才结束

### 阶段 6：输出
- 输出内部版（主工作文档），附可移交 patch-notes 的条目清单

### 阶段 7：提供写文件
- 询问写 `docs/CHANGELOG.md`（追加/覆盖/跳过），命中既有文件默认追加

## 输入/输出
- 输入：版本/sprint 编号、git 历史、sprint 报告、设计文档
- 输出：内部变更日志（可写 `docs/CHANGELOG.md`）+ 玩家向条目清单（供 `/patch-notes`）

## 约束
- 玩家向产出一律走 `/patch-notes`，本技能不自行翻译生成
- 平衡调整必须附设计意图
- 已知问题诚实透明

## 反例（不要这样）
- 自行翻译生成玩家向版本（那是 /patch-notes 的职责）
- 逐条罗列脏乱的 merge/revert 提交而不整理叙事
- 平衡调整只写数值不写意图
- 已知问题避而不谈

## 反合理化表（借口 → 反驳）
| 借口（会怎么说） | 反驳（为什么不对） |
|---|---|
| 「顺手把玩家向版本也写了，反正信息都有」 | 玩家向产出是 /patch-notes 的职责，内部与玩家向分离防泄漏（路径/开发者名）、保语气统一；混做会破坏职责边界。 |
| 「merge/revert 提交都列出来最全面」 | 应整理叙事而非逐条罗列脏提交，否则日志变成噪音而非变更说明。 |
| 「平衡改了个数值，写个 50→45 就够了」 | 平衡调整必须附设计意图，只写数值玩家无法理解为什么改。 |
| 「这个已知问题影响小，不写也没人知道」 | 已知问题须诚实透明，避而不谈会损害信任。 |

## Red Flags（违规信号）
- 自行生成玩家向版本而未移交 /patch-notes
- 逐条罗列 merge/revert 等脏提交而无叙事整理
- 平衡调整只写前后数值、无设计意图
- 已知问题章节缺失或避而不谈
- 未用 git rev-parse 确认仓库却强行读取提交历史

## Verification（证据化验证门）
- [ ] 产出内部版（含新功能提交/负责人/设计文档链接、改进、Bug 修复、平衡、技术债、杂项、已知问题、指标，逐项核对）
- [ ] 玩家向需求时已提示移交 /patch-notes（有移交记录，未自行生成）
- [ ] 平衡调整条目含设计意图（非仅数值）
- [ ] 已知问题章节存在且诚实列出（对照 bug 记录无遗漏）
