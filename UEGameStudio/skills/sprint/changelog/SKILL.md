# 内部变更日志

## 何时使用
- 生成某版本/sprint 的变更日志
- 需要内部版（技术）与玩家向版本两份

## 流程
### 阶段 1：解析参数
- 读版本或 sprint 编号（版本对应 git tag，sprint 对应日期范围）；`git rev-parse` 确认是 git 仓库，否则优雅中止

### 阶段 2：收集变更数据
- `git log [last-tag]..HEAD`（无 tag 读近 100 条）；读 sprint 报告与已完成设计文档理解上下文

### 阶段 3：分类变更
- 归入：新功能/改进/Bug 修复/平衡调整/已知问题/杂项
- 检查提交信息是否含任务引用（`[STORY-123]`、`#NNN` 等），统计无引用提交数

### 阶段 4：生成内部变更日志
- 按模板输出：新功能（含提交/负责人/设计文档链接）、改进、Bug 修复、平衡、技术债/重构、杂项、已知问题、指标

### 阶段 5：生成玩家向变更日志
- 玩家友好描述（体验而非实现）、改进、Bug 修复（玩家视角症状）、平衡（含设计意图）、已知问题（诚实）

### 阶段 6：输出
- 同时输出两份，内部版为主工作文档

### 阶段 7：提供写文件
- 询问写 `docs/CHANGELOG.md`（追加/覆盖/跳过），命中既有文件默认追加

## 输入/输出
- 输入：版本/sprint 编号、git 历史、sprint 报告、设计文档
- 输出：内部变更日志 + 玩家向变更日志（可写 `docs/CHANGELOG.md`）

## 约束
- 玩家向版本不得泄露内部代码引用、路径、开发者名
- 平衡调整必须附设计意图
- 已知问题诚实透明

## 反例（不要这样）
- 玩家向日志出现文件路径或开发者名
- 逐条罗列脏乱的 merge/revert 提交而不整理叙事
- 平衡调整只写数值不写意图
- 已知问题避而不谈

## 反合理化表（借口 → 反驳）
| 借口（会怎么说） | 反驳（为什么不对） |
|---|---|
| 「玩家看不懂，直接把提交信息贴上去就行」 | 玩家向版本必须转玩家语言、去内部引用，直接贴会泄露路径/开发者名并失去可读性。 |
| 「merge/revert 提交都列出来最全面」 | 应整理叙事而非逐条罗列脏提交，否则日志变成噪音而非变更说明。 |
| 「平衡改了个数值，写个 50→45 就够了」 | 平衡调整必须附设计意图，只写数值玩家无法理解为什么改。 |
| 「这个已知问题影响小，不写也没人知道」 | 已知问题须诚实透明，避而不谈会损害玩家信任。 |

## Red Flags（违规信号）
- 玩家向版本出现文件路径、内部代码引用或开发者名
- 逐条罗列 merge/revert 等脏提交而无叙事整理
- 平衡调整只写前后数值、无设计意图
- 已知问题章节缺失或避而不谈
- 未用 git rev-parse 确认仓库却强行读取提交历史

## Verification（证据化验证门）
- [ ] 同时产出内部版与玩家向版本，内部版为主工作文档（两份可见）
- [ ] 内部版含新功能（提交/负责人/设计文档链接）、改进、Bug 修复、平衡、技术债、杂项、已知问题、指标（逐项核对）
- [ ] 玩家向版本无文件路径/内部代码引用/开发者名（全量搜索确认）
- [ ] 平衡调整条目含设计意图（非仅数值）
- [ ] 已知问题章节存在且诚实列出（对照 bug 记录无遗漏）
