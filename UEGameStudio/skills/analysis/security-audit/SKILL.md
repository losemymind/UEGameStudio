# 安全审计

> **路径约定**：本技能中的 `src/`、`assets/`、`tests/`、`prototypes/` 等为项目级约定路径，落到 UE 项目时对应 `Source/<GameModule>/`、`Content/`、`Source/**/Tests/`、`Prototypes/`；完整映射见 `references/project-paths.md`。

## 何时使用
- 任何公开发布前（Polish→Release 门槛强制项）
- 启用任何在线/多人功能前
- 实现任何读写磁盘或网络的系统后
- 上报安全相关 bug 时

## 流程
### 1. 解析参数与范围
- `full`（发布前推荐）/ `network` / `save` / `input` / `quick`（只查高危，迭代用）；无参数走 full
- 读取技术偏好确定引擎、语言、目标平台、是否含多人

### 2. 派发安全工程师
- 用 Task 派发 security-engineer，传入范围、引擎语言、源码清单（src/、assets/data/、配置文件）

### 3. 审计六类
- 存档与序列化：加载前是否校验、路径是否来自用户输入（路径穿越）、是否校验和/签名、是否信任无边界数值、是否有 eval/动态执行
- 网络与多人：状态是否服务器权威、报文是否校验尺寸/类型/范围、是否限流、令牌是否明文、发布包是否暴露调试端点
- 输入校验：玩家字符串用于路径、日志注入、数值输入边界、成就/统计写入前校验
- 数据暴露：硬编码密钥、发布包调试符号/详细报错、敏感数据落盘/日志、内部路径暴露
- 作弊与反篡改：关键值是否只存内存、DLC 标志是否服务器校验、多人内存修改防护、排行榜提交校验
- 依赖与供应链：列出第三方插件、已知 CVE、来源是否可信

### 4. 分级发现
- 严重度：CRITICAL（远程执行/数据泄露/破坏多人完整性的易利用作弊）、HIGH、MEDIUM、LOW
- 状态：Open / Accepted Risk / Out of Scope

### 5. 生成报告
- 执行摘要（各严重度计数 + 发布建议 CLEAR TO SHIP / FIX CRITICALS FIRST / DO NOT SHIP）
- 按严重度分组的发现（SEC-NNN：类别/文件/描述/攻击场景/修复/工作量）
- 依赖清单、修复优先级顺序、复审计触发条件

## 输入/输出
- 输入：代码库 + 技术偏好 + 依赖清单
- 输出：安全审计报告（征得同意后写 `production/security/security-audit-[日期].md`）

## 约束
- 写报告前必须征得同意
- 绝不假设某模式安全，标记后让用户决定
- 接受风险是合法结果，但需记录决策
- 多人场景下 HIGH 应视为 CRITICAL 对待
- CRITICAL 未解决前禁止发布

## 反例（不要这样）
- 未经同意写报告文件
- 把客户端反作弊当作可行方案（应聚焦服务器端校验）
- 遗漏依赖/供应链审计
- 对已接受的风险不做记录

## 反合理化表（借口 → 反驳）
| 借口（会怎么说） | 反驳（为什么不对） |
|---|---|
| 「加个客户端反作弊就能挡住」 | 客户端校验不可信，必须聚焦服务器端校验 |
| 「这个风险先接受，不用记下来」 | 接受风险是合法结果但必须记录决策，否则责任不可追溯 |
| 「第三方插件都是常用的，不用查」 | 供应链审计是六类之一，遗漏 CVE/不可信来源会漏检 |

## Red Flags（违规信号）
- 未经同意直接写 security-audit 报告文件
- 报告无 SEC-NNN 编号或未按严重度分组
- 把客户端侧校验当作安全方案

## Verification（证据化验证门）
- [ ] 覆盖六类审计（存档/网络/输入/数据暴露/作弊/供应链）
- [ ] 发现含严重度（CRITICAL/HIGH/MEDIUM/LOW）与状态（Open/Accepted Risk/Out of Scope）
- [ ] 执行摘要含发布建议（CLEAR TO SHIP / FIX CRITICALS FIRST / DO NOT SHIP）
- [ ] 多人场景 HIGH 已按 CRITICAL 对待，CRITICAL 未解决前判 DO NOT SHIP
- [ ] 写报告前已征得同意
