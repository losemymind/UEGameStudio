# 范围蔓延检测

## 何时使用
- 用户质疑是否出现范围蔓延
- 里程碑或 sprint 收尾前核对范围
- 需要量化膨胀以支持裁剪决策

## 流程
### 1. 找到原始计划
- 按参数定位基线文档：feature → `design/gdd/[feature].md`；sprint → `production/sprints/`；milestone → `production/milestones/`
- 找不到基线则报告缺失并停止，绝不无基线对比

### 2. 读取当前状态
- 扫描相关代码文件、`git log` 相关提交、TODO/FIXME 未完成范围、当前 sprint 计划

### 3. 对比原始 vs 当前范围
- 列出原始范围、当前范围、范围新增（含来源/时间/是否合理/工作量）、范围删除（含原因/影响）
- 计算膨胀分数：原始项数、当前项数、新增项数（+X%）、删除项数、净变化

### 4. 风险与建议
- 评估进度/质量/集成三类风险
- 建议按 Cut / Defer / Keep / Flag 四类输出

### 5. 判定 verdict
- 净变化 ≤10% → PASS（在轨）；10–25% → CONCERNS（轻微蔓延）；25–50% → FAIL（显著蔓延）；>50% → FAIL（失控，重新规划并升级）

## 输入/输出
- 输入：基线计划文档 + 当前代码/提交状态
- 输出：范围对比报告 + 膨胀分数 + 风险 + verdict

## 约束
- 只读报告，不写文件
- 无基线不对比、不输出
- 必须量化变化（"+35% 项数"而非"感觉变大了"）
- 裁剪时优先保护核心玩家体验

## 反例（不要这样）
- 没有基线文档就凭空对比
- 用"感觉变大了"代替量化数据
- 把新增一律视为坏事，不区分发现的真实需求
