# 技术债登记与偿还排期

## 何时使用
- 扫描代码库新增债务
- 手动登记一条技术债
- 对现有债务登记表重排优先级
- 生成债务状态报告

## 流程
### 1. 解析子命令
- `scan`（扫描）/ `add`（新增）/ `prioritize`（重排优先级）/ `report`（报告）；无子命令则提示用法并给 verdict FAIL

### 2. 按模式执行
- **scan**：搜索 TODO/FIXME/HACK/@deprecated、重复代码块、超 500 行文件、超 50 行函数；分类为架构/代码质量/测试/文档/依赖/性能债务；征得同意后写入登记表（追加，不覆盖）
- **add**：询问描述、受影响文件、未修复影响；用 AskUserQuestion 收集分类与修复工作量（S/M/L/XL）；征得同意后追加
- **prioritize**：按 `(影响×频率)/修复工作量` 打分重排，推荐下个 sprint 纳入的项
- **report**：统计各分类数量、总工作量、较上次增减、趋势；标记滞留超 3 个 sprint 的项

### 3. 输出
- 登记表格式：`ID | 分类 | 描述 | 文件 | 工作量 | 影响 | 优先级 | 登记日期 | Sprint`
- 各模式给出 verdict：COMPLETE / BLOCKED（用户拒绝写）

## 输入/输出
- 输入：代码库 + `docs/tech-debt-register.md`
- 输出：更新后的登记表 / 债务报告

## 约束
- 写文件前必须征得同意
- 每条债务必须说明为何被接受（期限/原型/信息缺失）
- 扫描每 sprint 至少一次；滞留超 3 sprint 的项要么修复要么明确接受并记录原因
- 只追加不覆盖既有条目

## 反例（不要这样）
- 未经同意直接写登记表
- 把 FIXME 当普通 TODO 而不标注为"伪装的 bug"
- 只记债务不说明接受原因
- 覆盖既有登记条目导致历史丢失

## 反合理化表（借口 → 反驳）
| 借口（会怎么说） | 反驳（为什么不对） |
|---|---|
| 「直接写登记表就行，问用户太啰嗦」 | 写文件前必须征得同意，擅自写越过用户决策且产生不可逆改动 |
| 「FIXME 就是普通 TODO，归到待办就行」 | FIXME 是伪装的 bug，必须单独标注，否则债务严重度被低估 |
| 「记下债务就行，接受原因不用写」 | 每条债务必须说明为何被接受（期限/原型/信息缺失），否则无法判断何时该偿还 |
| 「重写登记表更整洁，覆盖旧的没关系」 | 只追加不覆盖，覆盖既有条目会导致历史丢失，无法追踪增减与趋势 |

## Red Flags（违规信号）
- 无子命令时未提示用法/未给 verdict FAIL
- 未经同意直接写登记表，或覆盖既有条目
- FIXME 被当作普通 TODO，未标注为「伪装的 bug」
- 新增债务未说明接受原因（期限/原型/信息缺失）
- 报告未标记滞留超 3 个 sprint 的项

## Verification（证据化验证门）
- [ ] 每条登记条目含 ID|分类|描述|文件|工作量|影响|优先级|登记日期|Sprint 且未覆盖既有条目（附 diff 证据）
- [ ] 每条债务写明接受原因，FIXME 被标注为「伪装的 bug」
- [ ] 写文件前已征得同意（附确认记录），各模式给出 verdict（COMPLETE / BLOCKED / FAIL）
- [ ] report 模式统计了各分类数量、总工作量、较上次增减，并标记滞留超 3 sprint 的项
