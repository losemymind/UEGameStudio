# 不稳定测试检测

## 何时使用
- Polish 阶段（多次运行后统计信号可靠）
- 开发者开始把 CI 失败当作"可能不稳定"而忽视时
- 需要对已隔离测试做诊断时

## 流程
### 1. 解析参数
- `[ci-log-path]`（分析特定日志）/ `scan`（扫描所有可用 CI 日志）/ `registry`（读取现有隔离清单给修复建议）/ 无参数自动检测

### 2. 定位 CI 日志数据
- GitHub Actions：`test-results/` 下 JUnit XML；Godot→GdUnit4 XML、Unity→NUnit XML、Unreal→`Saved/Logs/` 中 grep `Result: Success/Fail`
- 无日志则提示需多次运行收集，并停住询问

### 3. 解析测试结果
- JUnit XML：Grep `<testcase name=`、`<failure`、`<error`，解析 classname/name
- 纯文本日志：按引擎模式 grep PASS/FAIL
- 构建 `test_id → [run1, run2, run3, ...]` 表

### 4. 识别不稳定测试
- 无代码改动下既有 PASS 又有 FAIL 即为不稳定
- 阈值：>25% 高（立即隔离）、5–25% 中（尽快调查修复）、1–5% 低（监控，记 suspected）
- 归因：时序/异步、顺序依赖、随机种子、资源泄漏、外部状态、浮点比较、场景/预制加载竞态

### 5. 建议动作
- 高 → 隔离（加 skip 注解 + 登记，opt-in）
- 中 → 调查并修复（给根因与具体修法）
- 低 → 监控（记 suspected）

### 6. 生成报告与登记
- 会话内摘要：不稳定测试表（测试/系统/失败率/可能原因/建议）、干净测试、数据局限
- 征得同意后更新 `tests/regression-suite.md` 隔离段（只追加不删除）；可选写完整报告

## 输入/输出
- 输入：CI 日志 / 测试结果 XML / 回归套件隔离段
- 输出：不稳定检测结果 + 更新后的隔离清单 + 可选报告文件

## 约束
- 永不删除测试文件——隔离=注解+登记，非删除
- <3 次运行须标"疑似"而非"确认"
- 修复始终是目标，隔离是暂时的，即便隔离也要给出修复方向
- 更新回归套件与写报告都需显式批准

## 反例（不要这样）
- 删除测试文件而非隔离
- 少于 3 次运行就断言"确认不稳定"
- 静默隔离不告知团队
- 只隔离不给修复方向

## 反合理化表（借口 → 反驳）
| 借口（会怎么说） | 反驳（为什么不对） |
|---|---|
| 「直接删掉这个不稳定测试，省事」 | 永不删除测试文件，隔离=注解+登记 |
| 「跑了两三次都失败，肯定是稳定失败的」 | <3 次运行只能标"疑似"，不得断言确认 |
| 「先隔离起来，修复方向以后再说」 | 修复始终是目标，隔离是暂时的，隔离也要给修复方向 |

## Red Flags（违规信号）
- 出现删除测试文件的操作
- 少于 3 次运行就断言"确认不稳定"
- 隔离清单更新或报告写入未获批准

## Verification（证据化验证门）
- [ ] 已构建 test_id→[run1,run2,...] 表，基于无代码改动下 PASS+FAIL 并存判定
- [ ] 按阈值分级（>25% 隔离 / 5–25% 调查修复 / 1–5% 监控 suspected）
- [ ] <3 次运行已标"疑似"而非"确认"
- [ ] 隔离含 skip 注解+登记且给修复方向，更新回归套件前获批准
