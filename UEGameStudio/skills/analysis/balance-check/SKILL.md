# 平衡性检查

> **路径约定**：本技能中的 `src/`、`assets/`、`tests/`、`prototypes/` 等为项目级约定路径，落到 UE 项目时对应 `Source/<GameModule>/`、`Content/`、`Source/**/Tests/`、`Prototypes/`；完整映射见 `references/project-paths.md`。

## 何时使用
- 修改平衡相关数据或设计之后
- 用户要求生成平衡报告
- 怀疑某条策略退化或经济失衡时

## 流程
### 1. 识别平衡域
- 根据参数判断：战斗（DPS/击杀时间）、经济（资源收支）、成长（XP/强度曲线）、掉落（稀有度/保底），或直接给文件路径

### 2. 读取数据文件
- 读取 `assets/data/` 与 `design/balance/` 中该域相关文件，记录每个文件来源

### 3. 读取设计文档
- 读该系统的 GDD，理解设计目标、调优旋钮、期望数值范围（作为"正确"基线）

### 4. 执行分析
- 战斗：各强度档 DPS、击杀时间、是否存在严格占优选项、防御是否造成无敌态
- 经济：资源源头/漏点与流速、无限资源循环、金币漏点是否随产出缩放、是否存在永远不值得购买的物品
- 成长：XP/强度曲线、死区、强度尖峰、内容门槛是否对齐预期强度
- 掉落：各稀有度期望获取时间、保底数学、是否存在完全无用的掉落

### 5. 输出报告
- 分区：数据来源、健康摘要（HEALTHY/CONCERNS/CRITICAL ISSUES）、离群值表、退化策略、成长分析、建议表、需关注数值
- 报告后可选择：立即修最优先问题 / 存盘报告 / 停手

## 输入/输出
- 输入：平衡数据文件 + GDD
- 输出：平衡报告（含健康摘要与建议表），可选存盘

## 约束
- 报告以分析为主；修数值需引导用户，改动 GDD/ADR 定义的旋钮前提醒走变更传播
- 给出明确 verdict 级别（健康摘要三级）
- 建议必须含预期影响，不做空泛的"调高/调低"

## 反例（不要这样）
- 不读 GDD 就凭感觉判定"正确"数值
- 直接改数据文件而不先展示报告与征求同意
- 只列问题不给修复方向与影响
- 改动设计文档定义的数值却不提醒下游影响

## 反合理化表（借口 → 反驳）
| 借口（会怎么说） | 反驳（为什么不对） |
|---|---|
| 「经验告诉我就该是这个数值，不用读 GDD」 | 不读 GDD 就没有期望范围基线，凭感觉判定\"正确\"数值会引入隐性偏差 |
| 「直接改数据文件快，报告可以后补」 | 修数值必须先展示报告并征求同意，擅自改会绕过用户的变更传播决策 |
| 「建议写\"调高一点\"就够了」 | 建议必须含预期影响，空泛的\"调高/调低\"无法让用户评估后果 |
| 「改掉这个旋钮就好，下游不用管」 | 改动 GDD/ADR 定义的旋钮前必须提醒下游变更传播，否则破坏其他系统平衡 |

## Red Flags（违规信号）
- 报告缺少健康摘要三级（HEALTHY / CONCERNS / CRITICAL ISSUES）
- 未读该系统 GDD 就断言数值\"正确/错误\"
- 直接改数据文件而未先展示报告与征求同意
- 建议只有\"调高/调低\"而无预期影响

## Verification（证据化验证门）
- [ ] 报告含健康摘要三级，且与离群值/退化策略分析一致（附报告片段）
- [ ] 已读取该系统 GDD 并写明期望数值范围作为基线来源
- [ ] 每条建议附带预期影响，且对应到具体数值/公式旋钮
- [ ] 全程未擅自改动数据文件；若涉及 GDD/ADR 旋钮已提醒下游变更传播
