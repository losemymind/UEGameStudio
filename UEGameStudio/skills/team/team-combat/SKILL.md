# 战斗团队编排

## 何时使用
- 需要设计+实现+验证一个完整战斗功能
- 涉及玩法设计、AI、VFX、音效、QA 多角色协作
- 无战斗功能描述时直接输出用法并停止

## 流程
### 阶段 0：解析评审模式
- `--review` 参数 > `production/review-mode.txt` > 默认 `lean`

### 团队组成（哪些 agent 参与）
- **game-designer** — 设计机制、公式、边界情况
- **gameplay-programmer** — 核心玩法代码
- **ai-programmer** — NPC/敌人 AI 行为
- **technical-artist** — VFX、着色器、视觉反馈
- **sound-designer** — 音频事件、打击音、环境战斗音频
- **引擎专家（主）** — 校验架构与实现是否符合引擎惯用法
- **qa-tester** — 写用例并验证

### 阶段 1：设计（game-designer）
- 产出设计文档：机制概览、玩家幻想、详细规则、含变量定义的公式、边界情况、依赖、可调参数及安全范围、验收标准

### 阶段 2：架构（gameplay-programmer，涉及 AI 加 ai-programmer）
1. 设计类/接口/数据流，识别与现有系统的集成点
2. 引擎专家校验：类/组件结构是否惯用、是否应改用引擎原生系统、API 是否过期，产出引擎架构笔记并入架构
3. 决策点确认后才并行实现

### 阶段 3：实现（并行）
- gameplay-programmer 实现核心机制；ai-programmer 实现 AI；technical-artist 做 VFX/着色器；sound-designer 定音频事件与混音

### 阶段 4：集成
- 串联玩法代码、AI、VFX、音效；确保调参项数据驱动；验证与现有战斗系统协同

### 阶段 5：验证（qa-tester）
- 按验收标准写用例、测边界、验性能预算、提单

### 阶段 6：签署
- 汇总各成员结果，报 COMPLETE / NEEDS WORK / BLOCKED 及遗留问题负责人

## 输入/输出
- 输入：战斗功能描述、设计文档路径、相关代码、约束
- 输出：设计文档、架构草图、已实现代码/VFX/音效、测试结果、签署报告

## 约束
- 每阶段转换前用户须批准（决策点）
- 架构须经引擎专家惯用法校验后才实现
- 编排器不直接写文件，委托子 agent 并走写入协议
- 无参数时立即停止，不派生子 agent

## 反例（不要这样）
- 跳过架构评审直接写代码
- 调参值硬编码而非数据驱动
- 忽视引擎原生系统，用自定义实现重复造轮子
- 边界情况未在设计文档记录导致 QA 无从测起

## 反合理化表（借口 → 反驳）
| 借口（会怎么说） | 反驳（为什么不对） |
|---|---|
| 「直接写代码更快，架构评审浪费时间」 | 未经引擎专家校验可能用过期 API、重复造轮子或选错原生系统，后期返工远超评审成本 |
| 「调参值先硬编码，后面再抽成数据」 | 硬编码无法数据驱动平衡，QA 无从按验收标准测不同参数，且后续抽取易漏 |
| 「自定义实现比引擎原生系统省事」 | 忽视引擎原生系统是重复造轮子，长期维护与协同成本更高 |

## Red Flags（违规信号）
- 设计文档缺少边界情况、变量定义或安全范围
- 调参值以硬编码字面量出现在代码中
- 架构未经引擎专家校验就进入并行实现
- 无参数时仍派生子 agent

## Verification（证据化验证门）
- [ ] 设计文档含公式变量定义、边界情况、可调参数及安全范围、验收标准（逐项核对）
- [ ] 引擎专家架构笔记已并入架构文档（附笔记内容，而非口头确认）
- [ ] 调参项以数据驱动方式接入（附配置/资产引用，无硬编码字面量）
- [ ] 签署报告显式给出 COMPLETE/NEEDS WORK/BLOCKED 及遗留问题负责人
