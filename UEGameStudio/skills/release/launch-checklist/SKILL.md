# 发布上线检查清单

执行从变更窗口到上线后 72 小时的受控发布；不重复 release-checklist 的构建、认证、质量、安全与合规 readiness 审计。

> **职责边界**：必须读取 `production/releases/[version]-readiness.md`。其构建 ID、结论和签字均有效才可继续；缺失、过期、CONDITIONAL 条件未满足或构建 ID 不一致即 NO-GO。

> **三阶段**：本技能按时间线分为预发布（Pre-Launch）、上线日（Launch Day）、上线后（Post-Launch 72h）三个阶段，每个阶段有独立检查项与退出条件。前序阶段未通过不得进入下一阶段。

## 何时使用
- 版本准备就绪，即将发布到生产环境
- 需要确认所有平台认证、构建验证、QA 签字已完成
- 需要上线日执行清单与上线后监控计划
- 多部门（开发/QA/运维/市场/社区）需要协调上线节奏
- 发布后发现紧急问题，需要 Day-One Patch 热修复

## 流程
### 1. 解析参数
1. 读取目标平台（`pc`/`console`/`mobile`/`all`），默认 `all`；读取发布版本号
2. 读取 `--level full|pre-launch|launch-day|post-launch|day-one`（默认 `full`，跑全部三个阶段；`day-one` 模式进入 Day-One Patch 流程）

### 2. 加载项目上下文
1. 读取 `AGENTS.md`（技术栈、目标平台、团队结构）、里程碑文档与最近一次构建报告
2. 读取 `gate-check release` 结论、readiness 报告及同一构建 ID 的监控基线；任何不一致立即停止

### 3. 阶段一：上线授权验证（Pre-Launch Authorization）
1. **Readiness 引用**：只验证 readiness 报告存在、签字有效、构建 ID 一致、CONDITIONAL 条件已关闭；不重复构建审计
2. **平台认证状态**：按平台逐项确认认证状态
   - PC：Steam/Epic/GOG 审核状态、成就配置、云存档测试
   - Console：TRC/TCR/Lotcheck 通过、奖杯/成就提交、挂起/恢复测试、家长控制验证
   - Mobile：App Store 审核、Google Play 审核、隐私政策、数据安全标签、内购测试
3. **质量门**：零 S1 Bug、零 S2 或已批准例外、性能基准达标（FPS/内存/加载时间）、无回归、4+ 小时浸泡测试通过
4. **崩溃率**：崩溃率低于目标阈值（含平台差异）、无新增崩溃签名、崩溃上报已配置
5. **内容完整度**：所有计划功能已实现、本地化完成、配音/字幕就绪、商店素材已就绪
6. **上线授权**：release-manager、game-producer、qa-lead 与 liveops-sre 对变更窗口、灰度、监控和回滚签字

### 4. 阶段二：上线日检查（Launch Day）
1. **商店提交**：商店页面已发布、版本已提交审核（或已通过）、价格/区域配置正确、发售时间已设定
2. **CDN 部署**：CDN 缓存已预热、下载带宽已扩容、回源策略已配置、灰度发布百分比已设定
3. **服务器扩容**：预估玩家数峰值 × 1.5 以上容量、自动扩缩容已配置、数据库连接池已调优、备用节点已就绪
4. **监控配置**：实时指标仪表盘已配置（CCU/延迟/错误率/崩溃率）、告警规则已设置、On-call 排班已确认
5. **沟通计划**：社区公告已排期、社交媒体帖子已就绪、客服团队已培训、已知问题列表已发布
6. **上线决策**：Go/No-Go 最终确认，全部门签字（创意总监、技术总监、QA 负责人、制作人、发布经理、运营经理）

### 5. 阶段三：上线后监控（Post-Launch 72h）
1. **0–4 小时**：实时监控 CCU/崩溃率/服务器负载、每 30 分钟检查一次核心指标、社区反馈收集
2. **4–24 小时**：首日数据报告（CCU 峰值、崩溃率、平均游戏时长、付费转化）、性能回归检测、紧急 Bug 响应
3. **24–72 小时**：玩家反馈汇总、Bug 优先级排序、Hotfix 计划制定、Day-One Patch 准备工作
4. **回滚标准**：定义触发回滚的条件（崩溃率 >x%、服务器不可用 >y 分钟、严重数据损坏、重大安全漏洞）
5. **退出条件**：72 小时无 S1 新增、崩溃率稳定在目标范围内、服务器稳定运行、社区反馈可管理

## Day-One Patch 工作流（合并自 day-one-patch）

Day-One Patch 是上线后发现的紧急修复，在 Gold Master 之后、玩家大规模进入之前完成。它不同于常规 Hotfix——Day-One Patch 必须在首日玩家涌入前部署。

### 触发条件
- 上线后前 4 小时内发现的 S1（崩溃/阻塞/数据损坏）Bug
- 上线后 24 小时内发现的导致大量玩家无法正常游戏的 S2 Bug
- 平台认证要求的紧急合规修复
- 服务器端可热更的配置问题（走配置热更新，不进入 Day-One Patch 构建）

### Day-One Patch 流程
1. **紧急分类**（发现后 30 分钟内）：
   - S1-Critical（崩溃/数据损坏/安全漏洞）→ 立即进入 Hotfix 管道
   - S1-Blocker（阻塞主流程/无法进入游戏）→ 进入 Day-One Patch 管道
   - S2-Major（严重影响体验但可规避）→ 评估后进入 Day-One Patch 或推迟到首个常规补丁
   - 配置问题 → 走配置热更新，不阻塞构建
2. **修复窗口**（发现后 4 小时内）：
   - 仅修复 S1-Critical 和 S1-Blocker，S2 及以下不得进入 Day-One Patch
   - 修复必须是最小改动（单文件/单函数级别），禁止重构或连带修改
   - 每个修复必须附带回归测试，确认原始问题可复现且修复后不复发
3. **Hotfix 管道**（修复完成后 2 小时内）：
   - ✅ 在隔离分支上构建，不与主分支合并（避免污染准发布分支）
   - ✅ 完成修复后跑全量冒烟 + 受影响的回归套件
   - ✅ 4+ 小时浸泡测试（可缩短至 2 小时，但需技术总监批准）
   - ✅ 生成 Day-One Patch 变更日志（仅列修复的 Bug，不含新功能）
   - ✅ 平台认证快速通道（如有预认证协议）：提交变更说明，走加急审核
4. **部署与验证**（构建完成后）：
   - 灰度发布：先 5% 玩家推送，观察 30 分钟无异常 → 扩大到 100%
   - 部署后立即监控崩溃率、CCU、关键路径错误率
   - 30 分钟内无新增相关问题 → 确认 Day-One Patch 成功
5. **玩家沟通**：
   - 社区公告更新：说明 Day-One Patch 修复了哪些问题
   - 更新已知问题列表：移除已修复项，新增仍存在的问题
   - 客服团队同步：告知修复内容，更新 FAQ

### Day-One Patch 约束
- Day-One Patch 仅修复 Bug，不包含任何新功能、平衡调整或内容变更
- 修复必须是最小改动，禁止趁热重构或连带优化
- 每个修复必须附带回归测试，无回归测试的修复不得进入 Day-One Patch
- Day-One Patch 构建必须在隔离分支上，竣工后 cherry-pick 回主分支
- 上线后 72 小时外不再称为 Day-One Patch，走常规 Hotfix 流程
- S2 及以下 Bug 不得进入 Day-One Patch（除非技术总监特批）
- 未经全量冒烟 + 浸泡测试的 Day-One Patch 构建不得推送

### Day-One Patch 反例
- 趁 Day-One Patch 顺手加个小功能或调整平衡数值——Day-One Patch 仅修复 Bug
- 修复一个 S1 Bug 时顺便重构了相关模块——修复必须是最小改动
- 不写回归测试，说"修复很简单，不用测"——每个修复必须附带回归测试
- 不跑浸泡测试直接推送——必须经过 2+ 小时浸泡测试
- Day-One Patch 构建在主分支上修改——必须在隔离分支上构建

### 6. 保存清单
1. 展示执行计划与摘要；每个外部状态变更前请求授权，按步骤追加写入 `production/releases/[version]-launch-log.md`
2. Day-One Patch 模式额外写 `production/releases/day-one-patch-[version].md`

## 输入/输出
- 输入：目标平台、版本号、构建报告、质量门结论、性能基准、崩溃率数据
- 输出：launch log + 上线授权 + 部署/观察/回滚证据 + Day-One Patch 计划（如适用）

## 约束
- 阶段间有硬性依赖：前序阶段未通过不得进入下一阶段
- launch 不得代替 release-checklist；readiness 缺失或构建 ID 不一致必须 NO-GO
- 商店发布、CDN、扩容、灰度、回滚均为外部状态变更，每一步单独请求授权并记录操作者/时间/结果
- 平台认证项（TRC/TCR/Lotcheck、商店审核）是硬性门，缺一不可
- 性能基准须逐项核对（目标 FPS、内存、加载时间、无泄漏）
- 崩溃率阈值须按平台差异化设定，上线后 72 小时内必须持续监控
- 回滚标准必须在启动上线前就定义好，不可事后补
- 上线日全部门签字不可省略，缺少任一签字即判 NO-GO
- Day-One Patch 仅修复 Bug，不含新功能/平衡/内容变更
- Day-One Patch 修复必须是最小改动，附带回归测试
- Day-One Patch 构建必须在隔离分支上，全量冒烟 + 浸泡测试通过才可推送

## 反例（不要这样）
- 跳过平台认证检查直接上线——认证失败会被拒审或下架
- readiness 缺失时在 launch 内临时补一份自评并放行
- 服务器不扩容，"等玩家多了再加"——上线瞬间涌入可能压垮服务器
- 不设回滚标准，出了问题才讨论——缺少预定义回滚条件导致决策延迟、损害扩大
- 上线后疏于监控，第二天才看数据——关键的前 4 小时窗口被错过
- 沟通计划在上线当天才做——公告/帖子/客服培训应该在预发布阶段完成
- Day-One Patch 中加入新功能或平衡调整——Day-One Patch 仅修复 Bug
- Day-One Patch 修复时顺手重构了相关模块——修复必须是最小改动
- Day-One Patch 不写回归测试，不跑浸泡测试就推送——未经测试的修复可能引入新问题

## 反合理化表（借口 → 反驳）
| 借口（会怎么说） | 反驳（为什么不对） |
|---|---|
| 「认证去年就过了，这次改动不大不用重审」 | 认证是每次上线的硬性门，改动大小不是判断标准，被拒审会延迟整个发布。 |
| 「服务器昨天实测 5000 CCU 没问题，上线不用扩容」 | 上线日尖峰可能是实测的 3–5 倍，必须按预估峰值 ×1.5 扩容，不够再加。 |
| 「回滚标准等上线后再说，现在先赶发布」 | 回滚标准必须在启动上线前定义，事后补可能在紧急时刻无据可依、决策延迟。 |
| 「上线后先睡一觉，明天再看数据」 | 前 4 小时是关键窗口，必须每 30 分钟检查核心指标，延迟响应可能错过回滚最佳时机。 |
| 「社区公告随便发一条就行，不用提前准备」 | 公告/帖子/客服培训影响玩家第一印象，上线后补可能引发舆情。 |
| 「趁 Day-One Patch 顺手把这个小功能也加进去」 | Day-One Patch 仅修复 Bug，加功能违反最小改动原则，增加回归风险。 |
| 「这个 S1 Bug 修复很简单，不用写回归测试」 | 每个修复必须附带回归测试，无测试的修复可能在未来被破坏或在其他平台复发。 |
| 「修复 Bug 时顺便重构了相关代码，不算新功能」 | 重构不是最小改动，Day-One Patch 窗口期禁止任何非修复性修改。 |

## Red Flags（违规信号）
- 清单缺少平台认证条目（如 TRC/TCR/Lotcheck、商店审核项）
- 无 readiness 文件或构建 ID 不一致仍进入上线日动作
- 无条件或无回滚标准（如崩溃率阈值、不可用时长定义）
- 上线日缺少全部门签字人或签字人不全
- 上线后监控缺少 0–4 小时高频检查窗口
- 性能基准未逐项核对，只写"性能达标"而无具体数据
- Day-One Patch 中包含新功能、平衡调整或内容变更
- Day-One Patch 修复不带回归测试或不跑浸泡测试
- Day-One Patch 构建在主分支而非隔离分支上

## Verification（证据化验证门）
- [ ] 三阶段完整（授权/上线日/上线后 72h），且引用有效 readiness 与同一构建 ID
- [ ] 平台认证项按目标平台逐项列出，无遗漏（PC: Steam/Epic/GOG; Console: TRC/TCR/Lotcheck; Mobile: App Store/Google Play）
- [ ] 质量门含零 S1、零 S2 或批准例外、性能基准逐项、无回归、4+ 小时浸泡测试
- [ ] 回滚标准已定义（崩溃率阈值、不可用时长、严重数据损坏、重大安全漏洞的触发条件）
- [ ] 上线日签字人完整（创意总监/技术总监/QA 负责人/制作人/发布经理/运营经理）
- [ ] 输出含 Go/No-Go 决定
- [ ] Day-One Patch（如适用）仅含 Bug 修复，每个修复有回归测试，构建在隔离分支上
- [ ] Day-One Patch 经过全量冒烟 + 浸泡测试，有灰度发布计划

## 合并别名契约
- `day-one-patch` 是 `launch-checklist --level day-one` 的 legacy alias，不存在独立技能文件。
- alias 必须进入同一最小改动、隔离分支、回归/浸泡、灰度和监控流程。
