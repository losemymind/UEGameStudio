# 变更日志与补丁说明

## 何时使用
- 生成某版本/sprint 的**内部**变更日志（技术向，供团队/QA）
- 需要**玩家向**补丁说明（`--player-facing` 模式，供公开发布/社区）
- 需要记录新功能/改进/Bug 修复/平衡/技术债的完整明细

> **双模式**：本技能统一生成变更文档。默认产出**内部版**（开发者/QA 用）；`--player-facing` 模式产出**玩家向补丁说明**（面向公开）。两者共享数据收集/分类阶段，避免重复扫描 git 历史。内部版是玩家向的上游输入。

## 流程
### 阶段 1：解析参数
- 读版本或 sprint 编号（版本对应 git tag，sprint 对应日期范围）；`git rev-parse` 确认是 git 仓库，否则优雅中止
- 解析模式：`--player-facing`（玩家向补丁说明）/ 默认（内部版）

### 阶段 2：收集变更数据
- `git log [last-tag]..HEAD`（无 tag 读近 100 条）；读 sprint 报告与已完成设计文档理解上下文
- 玩家向模式：读 `production/releases/[version]/changelog.md` 或 `docs/CHANGELOG.md`（若已有内部版直接复用），回退 git log；无任何数据则提示先跑内部版并判 BLOCKED 停止

### 阶段 3：分类变更
- 归入：新功能/改进/Bug 修复/平衡调整/已知问题/杂项
- 检查提交信息是否含任务引用（`[STORY-123]`、`#NNN` 等），统计无引用提交数

### 阶段 4a：内部版输出（默认模式）
- 按模板输出：新功能（含提交/负责人/设计文档链接）、改进、Bug 修复、平衡、技术债/重构、杂项、已知问题、指标

### 阶段 4b：玩家向输出（--player-facing 模式）
1. 查语气指南与模板：技术偏好、`docs/PATCH-NOTES-STYLE.md`、`design/community/tone-guide.md`；无则默认玩家友好、非技术、热情但不夸大
2. 分类：新内容/玩法变更/质量优化/Bug 修复/性能/已知问题
3. 翻译：开发者语言转玩家语言（"重构伤害计算管线"→"改进命中判定精度"），移除纯内部变更，保留平衡前后值（50→45）
4. 风格：brief（要点式）/detailed（含上下文）/full（加开发者评论），默认 detailed
5. 审查：无内部黑话/ticket/sprint 引用、平衡含前后值、bug 描述玩家体验、语气匹配游戏风格

## 玩家向补丁说明章节规范（合并自 patch-notes）

玩家向补丁说明必须按以下章节组织，确保玩家能快速找到关心的内容。

### 必须章节
1. **New Features（新功能）**：新系统、新角色、新地图、新模式的名称与一句话描述。每个条目用玩家可理解的语言，不含"实现了"、"添加了"等开发用语，改为"现在你可以..."、"我们带来了..."。附解锁条件或使用方式。
2. **Bug Fixes（Bug 修复）**：描述玩家遇到的具体问题与修复后的表现。格式："修复了 [问题现象] 的问题"（而非"修复了 [函数名] 的 bug"）。影响范围大的 bug 标 `[Critical]` 或 `[Major]`。玩家反馈的 bug 标注 `[Community]`。
3. **Balance Changes（平衡调整）**：逐项列出数值变化，格式为"XX：从 A 调整到 B（+X%/-X%）"。附一句话调整意图，如"提升前期生存能力"、"降低后期统治力"。与原数值对比用 `→` 箭头。
4. **Quality of Life（体验优化）**：UI 改进、操作优化、流程简化等不改变玩法但改善体验的变更。每条说明"之前怎样 → 现在怎样"。
5. **Known Issues（已知问题）**：诚实列出当前版本已知但未修复的问题。每个问题必须含：现象描述、影响范围、临时规避方案（如有）、预计修复版本。不得隐瞒影响游戏体验的已知问题。
6. **Performance（性能优化）**（如有）：帧率改善、加载时间缩短、内存优化等。给出具体数据（如"加载时间从 45 秒减少到 30 秒"），不用"显著提升"等模糊表述。

### 可选章节
- **Events & Activities**：限时活动、赛季内容
- **Shop & Cosmetics**：商店更新、新皮肤/外观
- **Audio**：音效/音乐更新
- **Localization**：新增语言/翻译改进

### 补丁说明示例格式
```
## New Features
- **新角色「暗影行者」**：高机动性刺客，技能组围绕隐身与背刺，现已加入角色池
- **新地图「废弃工厂」**：5v5 对战地图，含多层垂直地形与传送带机制

## Bug Fixes
- [Critical] 修复了暗影行者使用「影遁」后可能卡入地形的严重问题
- [Community] 修复了商店界面在超高分辨率下按钮错位的问题（感谢玩家 @xyz 反馈）

## Balance Changes
- 暗影行者「影刃」伤害：85 → 75（↓12%），降低前期统治力
- 守护者「圣盾」冷却时间：12s → 10s（↑17%），提升团战频率

## Known Issues
- 暗影行者在「废弃工厂」传送带上有概率触发穿模，已定位，预计热修复中解决
- 部分老旧显卡在新地图中帧率偏低，建议降低阴影质量，将在下个版本优化
```

### 补丁说明约束
- 玩家向补丁说明**不得**出现：文件路径、类名、函数名、commit hash、ticket 编号、sprint 编号、开发者姓名
- 平衡调整必须有前后数值对比，不得只写"调整了 XX 的数值"
- Bug 修复描述必须从玩家视角出发，描述"玩家遇到了什么"而非"代码改了什么"
- 已知问题章节是强制性的，不得省略或隐藏影响游戏体验的问题
- 补丁说明发布前必须经 `community-manager` 语气审查

### 阶段 5：保存与移交
- 内部版：询问写 `docs/CHANGELOG.md`（追加/覆盖/跳过），命中既有文件默认追加
- 玩家向：请求写 `docs/patch-notes/[version].md`，并同时写 `production/releases/[version]/patch-notes.md` 内部归档；公开前经 `community-manager` 语气审查

## 输入/输出
- 输入：版本/sprint 编号、git 历史、sprint 报告、设计文档、语气指南（玩家向可选）
- 输出：内部变更日志（可写 `docs/CHANGELOG.md`）+ 玩家向补丁说明（可写 `docs/patch-notes/[version].md`）

## 约束
- 内部版可含文件路径/负责人；玩家向**不得**泄露内部代码引用、路径、开发者名、ticket/sprint 编号
- 平衡调整必须附设计意图（内部版）与前后值（玩家向）
- 已知问题诚实透明
- 无任何数据时玩家向判 BLOCKED，不臆造
- 玩家向补丁说明必须包含 New Features / Bug Fixes / Balance Changes / Quality of Life / Known Issues 五个必须章节
- 平衡调整玩家向必须有前后数值对比（A → B 格式），不得只写"调整了数值"
- Bug 修复描述必须从玩家视角出发，描述玩家遇到的问题

## 反例（不要这样）
- 玩家向出现文件路径/开发者名/ticket 号（应全部翻译为玩家语言）
- 逐条罗列脏乱的 merge/revert 提交而不整理叙事
- 平衡调整只写数值不写意图（内部版）或无前后值（玩家向）
- 已知问题避而不谈；无数据仍硬编玩家向补丁说明
- 未用 git rev-parse 确认仓库却强行读取提交历史
- 玩家向补丁说明缺少 Known Issues 章节（隐瞒已知问题）
- 平衡调整写"调整了 XX 的数值"而不给具体前后值
- Bug 修复写"修复了 XX 函数空指针异常"而非玩家视角描述

## 反合理化表（借口 → 反驳）
| 借口（会怎么说） | 反驳（为什么不对） |
|---|---|
| 「玩家看不懂，直接把提交信息贴上去就行」 | 玩家向必须转玩家语言、去内部引用，直接贴会泄露路径/开发者名/ticket 并失去可读性。 |
| 「顺手把另一个模式也写了，反正信息都有」 | 两模式目标受众不同：内部版要路径/负责人，玩家向要去内部引用；混做会泄漏或漏信息。按模式选择产出。 |
| 「merge/revert 提交都列出来最全面」 | 应整理叙事而非逐条罗列脏提交，否则日志变成噪音。 |
| 「没有数据，凭 git log 猜个大概也能写」 | 玩家向无数据必须判 BLOCKED 并提示先跑内部版，臆造会向玩家发布不实信息。 |
| 「这个已知问题影响小，不写也没人知道」 | 已知问题须诚实透明，避而不谈会损害信任。 |
| 「平衡调整写『调整了伤害数值』就行，玩家不关心具体数字」 | 平衡调整必须有前后值对比，玩家需要具体数字来判断英雄/武器的强度变化。 |
| 「Known Issues 章节没东西写就算了」 | Known Issues 是强制章节，即使没有已知问题也要写"本次更新无已知问题"，省略会被视为隐瞒。 |

## Red Flags（违规信号）
- 玩家向版本出现文件路径、内部代码引用、开发者名、ticket/sprint 编号
- 逐条罗列 merge/revert 脏提交而无叙事整理
- 平衡调整：内部版无设计意图、玩家向无前后值
- 已知问题章节缺失或避而不谈
- 玩家向无数据仍强行生成（未判 BLOCKED）
- 未用 git rev-parse 确认仓库却强行读取提交历史
- 玩家向补丁说明缺少 New Features / Bug Fixes / Balance Changes / Known Issues 任一必须章节
- Bug 修复使用开发视角描述（如"修复了空指针异常"）而非玩家视角

## Verification（证据化验证门）
- [ ] 内部版含新功能（提交/负责人/设计文档链接）、改进、Bug 修复、平衡、技术债、杂项、已知问题、指标（逐项核对）
- [ ] 玩家向输出无内部黑话/ticket/sprint 引用（全量搜索确认）
- [ ] 玩家向已应用语气指南或默认玩家友好；公开前有 community-manager 语气审查记录
- [ ] 平衡调整：内部版含设计意图、玩家向含前后值（如 50→45）
- [ ] 已知问题章节存在且诚实列出（对照 bug 记录无遗漏）
- [ ] 玩家向无数据场景已判 BLOCKED 并提示先跑内部版（无臆造内容）
- [ ] 玩家向补丁说明含 New Features / Bug Fixes / Balance Changes / Quality of Life / Known Issues 五个必须章节
- [ ] 所有 Bug 修复条目为玩家视角描述，无开发术语

## 合并覆盖
- **patch-notes**：玩家向补丁说明章节规范（New Features——新系统/角色/地图/模式、Bug Fixes——玩家视角问题描述+[Critical]/[Major]/[Community] 标注、Balance Changes——A→B 格式+数值变化百分比+调整意图、Quality of Life——体验优化/UI 改进/操作优化、Known Issues——诚实列出+现象描述+影响范围+临时方案+预计修复版本、Performance——具体数据对比），示例格式，约束（不得出现文件路径/类名/函数名/commit hash/ticket/开发者名、平衡必须有前后值、Bug 修复玩家视角、Known Issues 强制章节）
