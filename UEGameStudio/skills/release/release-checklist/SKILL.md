# 发布/上线清单

生成发布或上线校验清单，覆盖构建验证、质量门、内容完成度、平台/部门特定要求，产出 Go / No-Go 决定与签字。仅在用户显式以 `/release-checklist` 调用时运行，不自动触发。

> **双模式**：本技能统一发布与上线门。
> - **版本级（默认）**：每个发布版本跑一次（如 1.0、1.1、2.0），聚焦构建/认证/商店/质量，按平台（pc/console/mobile）差异化。
> - **最终上线（`--level launch`）**：一次真正的公开发布，跨部门（代码/内容/QA/商店/基础设施/社区营销/运营）。
> 顺序：先版本级（可多次）→ 最终上线（通常一次）；上线模式可引用版本模式的构建/认证结论，不重复校验。

## 何时使用
- 准备发布某个版本，需要验证构建/认证/商店/发布就绪度（默认版本级）
- 临近正式公开发布，需要覆盖所有部门的上线就绪与最终签字（`--level launch`）
- 需要 Go/No-Go 决定与签字

## 流程
### 解析参数
1. 读取模式：`--level version|launch`（默认 version）；dry-run 支持（只生成不写文件、不产签字）
2. 版本级：读取目标平台（`pc`/`console`/`mobile`/`all`），未指定默认 `all`

### 加载项目上下文
1. 读取 `AGENTS.md`（技术栈、目标平台、团队结构）与当前里程碑，确定应包含的功能与内容

### 扫描代码库健康（两模式共用）
1. 统计 `TODO`/`FIXME`/`HACK` 注释及位置，检查测试结果/CI 日志
2. 上线模式额外：遗留调试输出（`console.log`/`print()`）、占位资产（`placeholder`/`temp_`/`WIP_`）、硬编码测试/开发值（localhost、测试凭据、调试开关）

### 版本级清单（默认模式）
1. 通用块：代码库健康、构建验证（干净构建、零警告、资产齐全、构建大小、版本号、可复现）、质量门（零 S1、零 S2 或有批准例外、性能预算、无回归、4+ 小时浸泡测试）、内容完整度
2. 按平台追加：
   - `pc`：最低/推荐配置、键鼠/手柄、分辨率缩放、窗口/无边框/全屏、图形设置、Steam/Epic/GOG SDK、成就、云存档、Steam Deck
   - `console`：TRC/TCR/Lotcheck、平台手柄提示、挂起/恢复、用户切换、断网、存储满、家长控制、奖杯/成就、一方认证提交
   - `mobile`：商店指南、权限、隐私政策、数据安全标签、触控多尺寸、电池、后台行为、推送权限、内购、应用体积
3. 生成商店/分发与发布就绪块、Go/No-Go 结论与签字（QA 负责人、技术总监、制作人、创意总监）

### 上线级清单（--level launch 模式）
1. 按 7 大块生成可勾选清单：代码就绪（构建健康/代码质量/安全）、内容就绪（资产/文本与本地化/游戏内容）、质量保证（测试/平台认证/性能）、商店与分发（商店页/法律）、基础设施（服务器/分析与监控）、社区与营销（社区就绪/营销）、运营（团队就绪/Day-One 计划）
2. 安全检查覆盖：不暴露密钥、存档加密、网络加密（TLS/DTLS）、反作弊、服务端输入校验、隐私合规（GDPR/CCPA）
3. 产出 Go/No-Go 决定：READY / NOT READY / CONDITIONAL，列出阻塞项、条件项与签字人（创意总监、技术总监、QA 负责人、制作人、发布经理）

### 保存清单
1. 展示清单与摘要（总项数、阻塞项、条件项）；经确认写入 `production/releases/release-checklist-[version].md`（版本级）或 `production/releases/launch-checklist-[date].md`（上线级）；dry-run 只展示不写文件

### 后续步骤
1. 运行 `/gate-check` 获取正式门结论；通过 `/team-release` 协调最终签字

## 输入/输出
- 输入：项目上下文、版本、目标平台、代码库状态
- 输出：发布/上线校验清单 + Go/No-Go 决定 + 签字项

## 约束
- 仅显式调用，不基于上下文自动触发；零警告策略；FIXME 是潜在阻塞项需全部列出
- 性能预算须逐项核对（目标 FPS、内存、加载时间、无泄漏）
- 平台认证项（TRC/TCR/Lotcheck、商店指南）是硬性门，缺一不可
- 上线模式阻塞项必须在上线前解决；TODO/FIXME 上线前应为零（HACK 需有书面理由）

## 反例（不要这样）
- 忽略平台差异化要求，拿通用清单敷衍 console/mobile 认证项
- 只统计 TODO 数量不列具体位置——阻塞项无从追踪
- 跳过"无回归"验证——上一个版本能跑不代表这一版没退化
- 自动触发而非显式调用——非发布节点反复生成清单
- 上线模式只检查代码、忽略商店页/营销/社区/法律
- 上线模式忽略调试输出与硬编码测试值——把测试凭据或 localhost 带进生产构建
- 没有 Go/No-Go 与签字人就宣布"就绪"

## 反合理化表（借口 → 反驳）
| 借口（会怎么说） | 反驳（为什么不对） |
|---|---|
| 「通用清单差不多够用，console/mobile 认证项应付一下就行」 | 平台认证项（TRC/TCR/Lotcheck、商店指南）是硬性门，缺一不可，拿通用清单敷衍会卡认证。 |
| 「TODO 数量不多，不用列具体位置」 | 只统计数量不列位置，阻塞项无从追踪；FIXME 是潜在阻塞项必须全部列出。 |
| 「上一个版本能跑，这版不用重测无回归」 | 跳过无回归验证可能引入退化，上一版能跑不代表这一版没退化。 |
| 「上线模式只看代码就行，商店/营销等上线前一天再说」 | 上线门覆盖 7 大部门，忽略商店页/EULA/营销会在上线当天发现素材缺失。 |
| 「有几个调试输出和 localhost 没清理，不影响」 | 调试输出与硬编码测试值会把测试凭据/localhost 带进生产构建，是安全隐患。 |
| 「检查完给个『就绪』结论就完了，不需要签字人」 | 无 Go/No-Go 与签字人，上线决定缺少明确责任归属。 |

## Red Flags（违规信号）
- 版本级清单只有单一通用块，缺少按平台分块的认证/商店/分发条目
- 代码库健康只报 TODO/FIXME 数量，未给文件路径与行号
- 上线级清单缺少商店与分发、社区与营销、运营、基础设施部门
- 上线级未扫描调试输出、占位资产、硬编码测试值
- 缺少 Go/No-Go 结论或签字人字段（版本级三态 APPROVE/CONCERNS/REJECT 或缺签字人）
- 自动触发而非显式调用

## Verification（证据化验证门）
- [ ] 模式参数已解析（version/launch），清单含对应模式专属块（版本级按平台、上线级按 7 部门）
- [ ] 代码库健康项含 TODO/FIXME/HACK 的路径与位置，非仅计数；上线级含调试输出/占位/硬编码值扫描
- [ ] 质量门含零 S1、零 S2 或批准例外、性能预算逐项、无回归、4+ 小时浸泡测试
- [ ] 输出含 Go/No-Go 结论与签字人（版本级：QA 负责人/技术总监/制作人/创意总监；上线级：创意总监/技术总监/QA 负责人/制作人/发布经理）
- [ ] dry-run 模式只展示不写文件、不产签字条目
