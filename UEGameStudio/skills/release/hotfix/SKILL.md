# 热修复

## 何时使用
- 游戏不可玩、数据丢失、安全漏洞（S1）或重大功能损坏（S2）需要紧急修复
- 需要绕过正常 sprint 流程但保留审计痕迹
- 需要可回滚、可回迁的紧急变更

## 流程
### 评估严重度
1. 按 S1/S2/S3 标准评估并与用户确认；S3 及以下重定向到普通缺陷流程。

### 创建热修记录
1. 起草热修记录（问题、根因、修复、测试、审批、回滚计划），询问后写入 `production/hotfixes/`。

### 创建热修分支
1. 检测是否 git 仓库；确认后创建 `hotfix/[short-name]` 分支。

### 调查与实现
1. 只做解决该问题的最小改动，不重构、不加功能；跑受影响系统的定向测试并更新记录。

### 收集审批
1. 并行请求 lead-programmer / qa-tester / game-producer 三方 sign-off，全部 APPROVE 才继续。

### QA 重新准入门
1. 由 qa-lead 判定只需冒烟检查还是需要定向/全量 QA；门禁不可跳过。

### 更新缺陷状态并部署
1. 更新原缺陷为"已修复待验证"，输出部署摘要（含回滚计划、合并到 release + development 两分支）。

### 部署后验证
1. 跑 verify 确认修复；失败立即重新评估回滚并升级；48 小时内安排事后复盘。

## 输入/输出
- 输入：缺陷 ID 或描述、严重度确认。
- 输出：热修记录、热修分支、部署摘要、缺陷状态更新。

## 约束
- 仅显式 `/hotfix` 调用才运行，不基于上下文自动触发。
- 最小改动，禁止顺带重构/清理/加功能。
- 每个热修部署前必须有回滚计划。
- 热修分支须同时合入 release 与 development。
- 复杂到超 4 小时须升级给技术总监。

## 反例（不要这样）
- 把 S3 小问题当热修处理，绕过正常流程。
- 热修顺带重构无关代码。
- 无回滚计划就部署，或跳过 QA 重新准入门。
- 只合 release 分支不回迁 development。

## 反合理化表（借口 → 反驳）
| 借口（会怎么说） | 反驳（为什么不对） |
|---|---|
| 「这 bug 不大，走热修快一点」 | S3 及以下重定向普通缺陷流程，热修仅限 S1/S2，绕过正常流程会失去控制。 |
| 「顺手把这块重构一下」 | 最小改动原则，热修禁止顺带重构/清理/加功能。 |
| 「先上线，回滚计划后面补」 | 每个热修部署前必须有回滚计划，无回滚不可部署。 |
| 「合到 release 就行，development 以后再说」 | 热修分支须同时合入 release 与 development，否则回迁缺失。 |

## Red Flags（违规信号）
- 对 S3 缺陷发起热修而非重定向普通流程。
- 变更包含与缺陷无关的重构/新功能。
- 部署摘要缺少回滚计划，或只合一个分支。
- 跳过 QA 重新准入门或未经三方 APPROVE 就继续。

## Verification（证据化验证门）
- [ ] 严重度已按 S1/S2/S3 评估并与用户确认。
- [ ] 热修记录含问题/根因/修复/测试/审批/回滚计划，写入 production/hotfixes/。
- [ ] 分支为 hotfix/[short-name]，改动为最小集。
- [ ] 三方 sign-off 全 APPROVE，部署摘要含回滚计划与 release+development 双合并。
