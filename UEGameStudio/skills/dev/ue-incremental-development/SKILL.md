# UE 增量开发

## 流程
1. 读取 story、ADR、VERSION、模块/插件边界和测试证据路径；先通过 `dev-story readiness`。
2. 建切片图：每片只引入一个可观察行为，列前置、文件范围、编译/测试命令、回滚点与退出证据。
3. 顺序通常为契约/数据→纯逻辑→UE 集成→Blueprint/UI/内容→复制/存档→打磨；高风险项可先做最小 spike。
4. 可按用户约束压缩切片数量，但不得合并掉每片独立的编译、最小测试与回滚点；要求“最后一起编译”时必须拒绝。
5. 每片实施前记录工作树基线；委派 canonical 实现 agent，复制/GAS/World Partition 按需加专项 reviewer。
6. 每片完成立即编译相关 module、跑最小测试与受影响回归；失败则停在当前片，禁止叠加下一片。
7. 输出切片日志、改动、证据、回滚点和剩余风险；全部通过后进入 code-review 与 `dev-story done`。

## 约束
- 不以“最终一起编译”替代逐片验证；不混入无关重构。
- Content 二进制资产必须说明人工/Editor 证据，不能伪造文本 diff。

## 反例
- 一次改完十几个系统再首次编译。
- 当前片失败仍继续叠加下一片。
- 为方便顺手重构 story 范围外模块。

## 反合理化表
| 借口 | 反驳 |
|---|---|
| “一起改更快” | 失去故障定位和安全回滚点，集成成本更高。 |
| “资产没法测” | 可记录 Editor、Automation、截图或人工步骤证据。 |

## Red Flags
- 切片无独立可观察结果或回滚点。
- 未记录命令/退出码就称通过。
- 工作树出现无关文件。

## Verification
- [ ] 每片含范围、行为、验证命令、证据与回滚点。
- [ ] 失败片阻止后续片，且保留故障证据。
- [ ] 最终变更可追踪至 story 验收标准。
- [ ] 规划/只读模式下文件系统不变。
