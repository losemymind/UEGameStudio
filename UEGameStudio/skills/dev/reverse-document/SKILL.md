# 反向补文档

## 何时使用
- 先实现功能却未先写设计文档
- 接手了没有文档的代码库
- 把原型出来的机制正式化为设计文档
- 需要记录既有代码背后的"为什么"

## 流程
### 解析参数
1. 解析类型（design / architecture / concept）与路径（目录或文件）。

### 分析实现
1. design：提取机制、规则、公式、玩法数值、状态机、边界情况、依赖。
2. architecture：识别模式、技术决策、耦合、性能特征、约束与取舍。
3. concept：识别核心机制、涌现玩法、成败经验、可行性洞察、玩家幻想。

### 提出澄清问题
1. 不描述代码，而是问"意图"：某资源系统是为了节奏控制还是策略深度？某机制是核心支柱还是辅助？数值指数缩放是故意还是需调？

### 呈现发现
1. 展示发现的机制、公式、不明确意图区，等待用户澄清后再起草。

### 用模板起草文档
1. 按类型选模板与输出路径（design→GDD、architecture→ADR、concept→概念文档）。
2. 记录"有什么"（实现）、"为什么"（已澄清意图）、"缺什么"（未处理边界）、"后续工作"。

### 展示草稿并请求批准
1. 展示关键小节与我方补充/标注未完成的段落，询问是否写入。

### 写入文档并标注元数据
1. 加 frontmatter（status: reverse-documented、source、date、verified-by）与"本文件由实现反推"提示。

### 标记后续工作
1. 输出建议的后续（平衡检查、补 ADR、补边界情况），询问是否现在处理。

## 输入/输出
- 输入：类型 + 目标路径、用户对意图的澄清。
- 输出：GDD / ADR / 概念文档（带 reverse-documented 元数据）。

## 约束
- 先分析、问意图、再起草，绝不臆断"为什么"。
- 展示草稿并征得同意后才写文件。
- 明确区分"已有实现"与"补充的意图/遗漏"。

## 反例（不要这样）
- 只把代码翻译成人话，而不问设计意图。
- 未经澄清就自行编造"设计意图"写进文档。
- 不标注反向文档状态，让人误以为是原生设计文档。

## 反合理化表（借口 → 反驳）
| 借口（会怎么说） | 反驳（为什么不对） |
|---|---|
| 「代码都看得懂，直接写文档就行」 | 只把代码翻译成人话不问设计意图，产出的是「是什么」而非「为什么」。 |
| 「意图我推断一下就补上」 | 未经澄清编造设计意图会污染文档，须先问「意图」再起草。 |
| 「反推的文档不用标注」 | 不标注 status: reverse-documented，会让人误以为是原生设计文档。 |

## Red Flags（违规信号）
- 文档正文只描述代码行为，没有记录「为什么」与「缺什么」。
- 未经澄清就填写设计意图/取舍。
- 写出的文档没有 frontmatter（status: reverse-documented、source、date、verified-by）与反推提示。

## Verification（证据化验证门）
- [ ] 类型（design/architecture/concept）与目标路径已解析，模板与输出路径匹配。
- [ ] 起草前先呈现发现并等待澄清，区分「已有实现」与「补充意图/遗漏」。
- [ ] 文档含「有什么/为什么/缺什么/后续工作」四部分。
- [ ] 写入文档含 frontmatter 与「由实现反推」提示，且经批准才写。
