# 垂直切片构建

制作一个从开始到结束的完整可玩游戏循环——垂直切片——并打磨到可发布质量。垂直切片是向投资者/发行商/内部决策者证明"这个游戏可以做成"的关键演示。

> **垂直切片 vs 原型**：原型验证"核心机制是否好玩"（用最少的代码和资产），垂直切片证明"完整游戏体验是否成立"（可发布质量的完整循环）。原型是 PROCEED/PIVOT/KILL，垂直切片是 GO/NO-GO 进入全面生产。

## 何时使用
- 原型验证通过后，需要证明完整游戏循环可以打磨到可发布质量
- 需要向投资者/发行商展示可玩演示
- 进入全面生产前需要最终确认技术管线与艺术方向
- 需要确立"质量标杆"——后续所有内容的品质参照

## 流程
### 1. 定义垂直切片
1. 读取游戏概念文档（game-concept）与核心循环定义
2. 确定垂直切片的范围：**一个完整游戏循环**，从 startup 到 shutdown 全部覆盖
   - 包含：启动→主菜单→核心玩法（一个完整关卡/一局/一个任务）→结算→返回菜单
   - 必须包含：UI 流程、音频、视觉特效、手柄/键鼠适配、性能达标
3. 明确写入"不包含"的内容（如：全部关卡、多人联机、成就系统、云存档、内购）

### 2. 范围选择
1. 用以下标准筛选切片内容：
   - 最能代表游戏核心体验的关卡/场景
   - 视觉表现力最强的资产
   - 技术上最具挑战性的功能（验证管线可行）
2. 范围控制：最多 3–5 个核心机制，不贪多；砍掉非核心的旁支系统
3. 输出范围文档：包含清单、排除清单、预期体验时长（通常 10–30 分钟）

### 3. 打磨目标
1. 建立"可发布质量"标准：
   - **视觉**：最终画质或接近最终画质，光照/后处理/材质达到目标
   - **音频**：完整的音效和音乐（可使用临时资源但质量必须达标）
   - **UI**：最终 UI 风格，所有界面完整可用
   - **动画**：无 T-Pose、无动画跳帧、过渡平滑
   - **Bug**：零崩溃、零阻塞性 Bug、零视觉穿模
2. 对标参考游戏建立品质参照

### 4. 验证标准
1. 垂直切片必须证明以下四项：
   - **核心循环成立**：玩家可以完成完整循环并获得满足感
   - **视觉目标达成**：画质达到或接近目标，艺术风格一致
   - **性能目标达成**：目标平台达到目标帧率（如 30/60 FPS），内存不超预算，加载时间在目标内
   - **技术管线验证**：资产导入→编辑→Cook→打包全流程跑通

### 5. UE 特定操作
1. **烹饪与打包**：
   - 使用 Shipping 构建配置进行性能测试（Development 配置性能不可靠）
   - 运行 `Cook` 命令验证所有资产可正常烹饪，无引用丢失
   - 打包为目标平台的可执行文件，在目标设备上测试
2. **演示构建配置**：
   - 创建专门的演示构建配置：移除调试菜单、跳过启动 Logo、锁定分辨率/画质
   - 设置自动演示模式（若无操作 30 秒后自动播放）
   - 配置启动参数：`-game -resx=1920 -resy=1080 -fullscreen`
3. **性能分析**：
   - 使用 `stat fps`、`stat unit`、`stat memory` 确认性能指标
   - 使用 Unreal Insights 录制并分析性能瓶颈
   - 使用 `obj list`、`memreport` 排查内存问题
4. **资产验证**：
   - 资产引用检查器（Reference Viewer）确认无丢失引用
   - 使用 Asset Audit 检查资产大小与合规性
   - 确保所有资产命名遵循项目规范

### 6. 试玩与反馈
1. 组织内部试玩（团队成员 + 非团队成员），收集反馈
2. 记录：最佳时刻、最糟时刻、困惑点、帧率/卡顿感知
3. 逐项修复后复测——垂直切片不允许有"已知但没修"的阻塞问题

### 7. 输出与决策
1. 撰写垂直切片报告：范围达成度、性能数据、视觉对比、试玩反馈摘要
2. 产出 GO/NO-GO 决策：全面生产、先修复后重评、调整方向
3. 保存 canonical 阶段产物到 `production/vertical-slice/REPORT.md`；历史测量附件可按日期放 `production/vertical-slice/evidence/`
4. GO 后该垂直切片即为"质量标杆"，后续所有内容的品质不得低于此基准

## 输入/输出
- 输入：游戏概念文档、核心循环定义、对标参考游戏、目标平台与性能预算
- 输出：`production/vertical-slice/REPORT.md`、可玩演示构建、性能/试玩证据、GO/NO-GO 决策

## 约束
- 垂直切片代码**不可**直接重构进生产——生产实现应从零重写，但可以复用架构设计
- 资产可以复用（垂直切片资产应达到生产质量），但必须经资产审核
- 范围必须严格限定：一个完整循环，3–5 个核心机制，不贪多
- 性能测试必须在 Shipping 构建上进行，Development 配置性能不可靠
- 零崩溃、零阻塞性 Bug 是硬性要求，不可妥协

## 反例（不要这样）
- 做一个"技术演示"而非完整游戏循环——缺少 UI/结算/菜单流程，不能证明游戏体验
- 范围无限扩大，试图包含所有系统——垂直切片不是完整游戏，只证明核心循环
- 用 Development 配置测性能然后说"正式版会优化"——Development 配置性能不可靠，必须在 Shipping 上测
- 把垂直切片代码直接重构进生产——生产实现应从零重写，切片代码为快速迭代牺牲了架构
- 试玩后不修阻塞问题就宣布 GO——垂直切片不允许有"已知但没修"的阻塞问题

## 反合理化表（借口 → 反驳）
| 借口（会怎么说） | 反驳（为什么不对） |
|---|---|
| 「做个技术演示就行，不用管 UI 和结算画面」 | 垂直切片必须是完整游戏循环，缺少 UI/结算/菜单不能证明游戏体验成立。 |
| 「多放几个系统进去，展示内容更丰富」 | 范围必须严格限定 3–5 个核心机制，贪多会分散精力，每个都打磨不到可发布质量。 |
| 「Development 配置跑得还行，Shipping 优化后面再说」 | Development 有大量调试开销，性能数据不可靠；必须在 Shipping 构建上测试。 |
| 「切片代码写得不错，直接拿来开发生产版本」 | 切片代码为快速迭代牺牲了架构，只能复用设计思路。生产实现应从零重写。 |
| 「有几个小 Bug 不影响演示，先宣布 GO」 | 垂直切片不允许有"已知但没修"的阻塞问题，零崩溃、零阻塞性 Bug 是硬性要求。 |

## Red Flags（违规信号）
- 垂直切片缺少完整游戏循环（只有核心玩法，无 UI/结算/菜单流程）
- 范围超过 5 个核心机制，或包含明确标记为"不包含"的系统
- 性能测试在 Development 配置上进行，而非 Shipping 构建
- 垂直切片代码被直接导入生产源文件
- 试玩后存在未修复的阻塞性 Bug，仍宣布 GO
- 缺少正式的性能报告（帧率/内存/加载时间数据）

- [ ] 垂直切片代码未导入生产源文件（可核验无 import 关系）
