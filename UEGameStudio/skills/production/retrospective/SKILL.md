# Sprint/里程碑复盘

## 何时使用
- sprint 或里程碑结束
- 需要沉淀速率、阻塞、模式与改进动作

## 流程
### 阶段 1：解析参数
- 区分 sprint 复盘（sprint-N）与里程碑复盘（milestone-name）

### 阶段 1b：检查既有复盘
- glob 既有复盘文件；命中则让用户选更新（沿用并修订）或全新（归档旧文件）

### 阶段 2：加载数据
- 读 sprint/里程碑计划；优先读 sprint-status.yaml 作为完成度权威来源
- 无数据则让用户选手动提供或停止
- 用 git log 看实际提交（`--since` 对齐 sprint 时长）

### 阶段 3：分析完成与趋势
- 对比计划与实际：按计划完成/修改后完成/顺延/中途新增/移除
- 统计 TODO/FIXME/HACK 并与上轮对比，判断技术债增减
- 读既有复盘查行动项是否落地、问题是否复发、速率趋势

### 阶段 4：生成复盘
- 指标表、速率趋势、做得好/做得差（数据支撑、归因系统不追责）、阻塞表、估算准确度、顺延分析、技术债状态、上轮行动项跟进、下轮行动项、流程改进、总结

### 阶段 5：保存
- 请求写 `production/retrospectives/retro-sprint-[N]-[date].md`

### 阶段 6：下一步
- 决策点询问是否带数据启动 sprint-plan new；里程碑复盘则跑 gate-check

## 输入/输出
- 输入：sprint/里程碑计划、sprint-status.yaml、git log、既有复盘
- 输出：复盘文档（指标、趋势、阻塞、行动项、流程改进）

## 约束
- 行动项限 3-5 条，每条有负责人与截止
- 聚焦系统性问题，不追责个人
- 具体可衡量，避免空泛
- 检查上轮行动项是否落地

## 反例（不要这样）
- 空泛结论（"沟通要加强"）而非数据支撑的洞察
- 行动项超 5 条且无负责人/截止
- 追责个人而非归因流程
- 忽略 sprint-status.yaml 而只看 markdown

## 反合理化表（借口 → 反驳）
| 借口（会怎么说） | 反驳（为什么不对） |
|---|---|
| 「沟通要加强这种结论大家都能懂」 | 约束要求具体可衡量，空泛结论无法转化为可执行的流程改进。 |
| 「这次问题有点多，列 8 条行动项才够」 | 行动项限 3-5 条且每条有负责人与截止，超量会导致无人认领、无从跟进。 |
| 「这个 bug 是张三漏测的，得点名」 | 复盘聚焦系统性问题、归因系统不追责，点名会破坏安全感并掩盖流程缺陷。 |
| 「markdown 计划就够了，不用读 sprint-status.yaml」 | sprint-status.yaml 是完成度权威来源，跳过它会误判实际完成度，复盘结论失真。 |

## Red Flags（违规信号）
- 结论是空泛口号（如"沟通要加强"）而非数据支撑的洞察
- 行动项超过 5 条，或缺少负责人/截止
- 结论点名追责个人而非归因系统/流程
- 未优先读取 sprint-status.yaml 作为完成度来源
- 未跟进上轮行动项是否落地、问题是否复发

## Verification（证据化验证门）
- [ ] 复盘文档含指标表、速率趋势、阻塞表、顺延分析、技术债状态、上轮行动项跟进（逐项核对）
- [ ] 行动项数量 3-5 条，且每条有负责人与截止（逐条检查字段非空）
- [ ] 洞察结论有数据支撑（引用具体指标/提交/阻塞证据），无空泛口号
- [ ] 已确认优先读取 sprint-status.yaml；git log 用 --since 对齐了 sprint 时长
- [ ] 全程无追责个人的表述，归因落在系统/流程
